Native packages use the same `@import(...)` syntax as source modules, but the
import resolves package metadata and a compiled shared library rather than a
single `.mog` source file.

## A complete local example

The `math` used below is the reference native package at
`packages/examples/math/` in the Mog runtime repository. `./build.sh` builds it
into the repository's package output, which is why the bare `"math"` import can
resolve when running examples from a source checkout.

<Tabs syncKey="native-math-example">
	<TabItem label="app.mog">
	```rust
	const math = @import("math")

	print(math.addI64(1i64, 2i64))
	print(math.MEANING_OF_LIFE)
	print(math.greet("Turing"))
	```
	</TabItem>
	<TabItem label="package.api.mog">
	```rust
	package math

	@doc("Reference constant export.")
	const MEANING_OF_LIFE i64

	@doc("Add two i64 values.")
	fn addI64(lhs i64, rhs i64) i64

	@doc("Return a greeting for the provided name.")
	fn greet(name str) str
	```
	</TabItem>
	<TabItem label="mog.toml">
	```toml
	kind = "native"
	import_name = "math"
	namespace = "examples"
	name = "math"
	version = "0.1.0"
	abi_version = 3
	mog_runtime = "^0.1.0"
	```
	</TabItem>
</Tabs>

`package.api.mog` is the public Mog-facing contract. The corresponding
`package.cpp` implements and registers those functions and constants through
the native package ABI.

<Aside type="note" title="Local reference package, not the official math package">
	The independently released source package uses the canonical import
	`github.com/moglang/math`. See [Official Packages](/docs/packages/official-packages/)
	for that package and the rest of the project-maintained catalog.
</Aside>

Bare import names such as `"math"` resolve through package metadata. Canonical
module paths such as `"github.com/moglang/fs"` resolve installed dependencies.
Path-like imports such as `"./math.mog"` stay source-module imports.

## Search paths

The current interpreter searches for packages in:

- `build/packages` relative to the interpreter binary
- any roots passed with `--package-path`
- `packages/` relative to the importing source file or current working directory

You can add extra roots explicitly:

```bash
mog run --package-path /path/to/packages app.mog
```

## Opaque package types

Packages can expose opaque handle types through `package.api.mog`.

```mog
const counter = @import("counter")

const first counter.Counter = counter.create(10i64)
const second counter.Counter = counter.create(20i64)

print(counter.read(first))
print(counter.add(second, 5i64))
```

Those values are package-managed handles, but the type checker still tracks
their package identity.

## API declaration files

Native packages can ship `package.api.mog` for:

- readable public signatures
- editor navigation and hover docs
- public opaque type declarations

The reference packages under `packages/examples/` are the best examples in this
repo.

## Installing published native packages

Published native packages use the same dependency workflow as source packages,
but installs may need to choose between a prebuilt artifact and a local source
build.

Useful flags:

- `mog install --target <triple>` to select a specific native target
- `mog install --prefer-prebuilt` to stay on registry-published binaries when available
- `mog install --no-native-build` to reject source fallback
- `mog install --cmake-toolchain <path>` to allow non-host source-build fallback

When a registry entry only publishes source for the requested target, Mog
records `build_from_source = true` and the selected target in `mog.lock`.
Subsequent `mog run --locked --target <triple>` executions can reuse the cached
install without rebuilding.

## Validating a package

Validate a package directory against its manifest and compiled shared library:

```bash
mog validate-package packages/examples/math
mog validate-package packages/examples/counter
```

The current validator checks package ID syntax, reserved `mog` usage,
manifest/ABI compatibility, registration metadata, and exported native
signature parsing.
