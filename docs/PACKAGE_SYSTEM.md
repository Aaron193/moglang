# Mog Package System

This document is the user-facing guide for Mog's package system. For the
implementation roadmap and historical phase tracking, see
`../PACKAGE_SYSTEM_PLAN.md`.

The package manager is V1-complete for normal project use: local packages,
workspace packages, git dependencies, registry packages, source packages,
native packages, lockfiles, offline installs, hosted registries, publishing,
signing, registry trust, policy enforcement, and audit workflows are supported.

Official ownership, source/native selection, and compatibility requirements are defined in [Package Policy](PACKAGE_POLICY.md). `std/...` is reserved for language-owned modules; shared code should import official packages using canonical `github.com/moglang/...` paths.

## Quick Start

Create a project:

```bash
./build/interpreter init my-app
```

Add dependencies:

```bash
./build/interpreter add hello
./build/interpreter add acme/http@^1.2.0
./build/interpreter add github.com/acme/math@v1.0.0
./build/interpreter add --path packages/examples/hello
./build/interpreter add --git https://example.com/acme/util.git --tag v1.0.0
```

Install and run:

```bash
./build/interpreter install
./build/interpreter run app.mog
```

`mog run` is install-aware. If the project has declared dependencies, it
installs them before execution and then runs against generated install
metadata.

## Project Files

A package-managed project uses:

- `mog.toml` for project metadata, dependencies, registries, policy, scripts,
  workspace members, and native toolchains
- `mog.lock` for the exact resolved dependency graph
- `.mog/install/registry.toml` for installed package metadata consumed by the
  compiler, runtime, and language server
- `.mog/install/packages/` for project-local materialized packages

`mog.lock` and `.mog/install/registry.toml` are generated by the package
manager. Commit `mog.lock` for reproducible installs. Do not hand-edit it.

## Dependency Sources

Dependencies are declared under `[dependencies]`, `[dev-dependencies]`, or
`[build-dependencies]`.

### Local path dependencies

```bash
./build/interpreter add --path packages/examples/hello
```

Generated manifest shape:

```toml
[dependencies]
hello = { path = "packages/examples/hello", package = "examples:hello", version = "0.1.0" }
```

### Workspace dependencies

Workspace roots declare members:

```toml
[workspace]
members = ["packages/hello", "packages/math"]
```

Then add a workspace package:

```bash
./build/interpreter add --workspace --package examples:hello
```

Generated manifest shape:

```toml
[dependencies]
hello = { workspace = true, package = "examples:hello", version = "0.1.0" }
```

Workspace-root commands write the shared `mog.lock` and
`.mog/install/registry.toml` at the workspace root.

### Git dependencies

Go-style Git module imports use the hosted repository path as the import path:

```mog
const math = @import("github.com/acme/math")
print(math.Add(40, 2))
```

Add the module by tag:

```bash
./build/interpreter add github.com/acme/math@v1.0.0
```

Generated manifest shape:

```toml
[dependencies]
"github.com/acme/math" = { version = "v1.0.0" }
```

`mog install` resolves the module to Git, pins the exact commit in `mog.lock`,
and materializes it under `.mog/install/packages/github.com/acme/math`.

Git native packages are built from source through the CMake-native package contract and
are pinned by commit in `mog.lock`. They must include `package.cpp` or
`CMakeLists.txt`, `package.api.mog`, and the public `NativePackageAPI.hpp` ABI
header. Git dependencies do not consume prebuilt native binaries; publish
target-specific prebuilt artifacts through a registry instead.

Git dependencies require exactly one selector: `--rev`, `--tag`, or
`--branch`.

```bash
./build/interpreter add --git https://example.com/acme/util.git --tag v1.0.0
```

Mog checks out the selected ref, reads the package manifest, fills missing
package metadata, and pins the resolved commit in `mog.lock`.

Generated manifest shape:

```toml
[dependencies]
util = { package = "acme:util", version = "1.0.0", git = "https://example.com/acme/util.git", tag = "v1.0.0" }
```

### Registry dependencies

Registry packages use canonical package IDs and semantic version requirements.

```bash
./build/interpreter add acme/http@^1.2.0
./build/interpreter add --registry internal acme/http@^1.2.0
```

Supported version requirements are exact `x.y.z`, caret `^x.y.z`, and tilde
`~x.y.z`.

Generated manifest shape:

```toml
[registries.internal]
index = "./registry"

[dependencies]
http = { package = "acme:http", version = "^1.2.0", registry = "internal" }
```

### Dependency groups

Use `--dev` or `--build` to place an added dependency in the matching group:

```bash
./build/interpreter add --path packages/test-helper --dev
./build/interpreter add --path packages/codegen --build
```

`mog test` installs runtime and dev dependencies. `mog build` installs
runtime and build dependencies.

## Installing, Updating, and Running

Install dependencies:

```bash
./build/interpreter install
```

Update dependencies within manifest constraints:

```bash
./build/interpreter update
```

Run with automatic dependency installation:

```bash
./build/interpreter run app.mog
```

Run package-aware scripts declared in the root manifest:

```toml
[scripts]
test = "tests/main.mog"
build = "tools/build.mog"
```

```bash
./build/interpreter test
./build/interpreter build
```

## Lockfiles and Offline Installs

Use `--locked` in CI or release workflows:

```bash
./build/interpreter install --locked
./build/interpreter run --locked app.mog
```

`--locked` requires the existing `mog.lock` to match `mog.toml`; it does not
refresh dependency versions.

Use `--offline` when all required artifacts are already local or cached:

```bash
./build/interpreter install --offline
```

Offline installs support local path/workspace graphs, cached git dependencies,
and cached registry packages.

## Cache Commands

Inspect cache/store locations:

```bash
./build/interpreter cache status
./build/interpreter cache path user
./build/interpreter cache path project
./build/interpreter cache path registry
./build/interpreter cache path git
```

Prune caches:

```bash
./build/interpreter cache prune --dry-run
./build/interpreter cache prune
```

Mog uses a user cache when available and falls back to project-local cache
storage when the preferred user cache path cannot be used.

## Package Manifests

Package manifests use `mog.toml`. Legacy `package.toml` is still accepted as
an input compatibility path.

Source package example:

```toml
kind = "source"
import_name = "util"
namespace = "acme"
name = "util"
version = "1.0.0"
license = "MIT"
description = "Utility package."
entry = "src/main.mog"
dependencies = []
```

Native package example:

```toml
kind = "native"
module = "github.com/moglang/window"
import_name = "window"
version = "0.1.0"
license = "MIT"
abi_version = 3
mog_runtime = "^0.1.0"
description = "Window package."
dependencies = []

[native]
entry = "package"
build = "cmake"
targets = ["linux-x86_64-gnu"]

[system-dependencies]
sdl2 = { version = ">=2.0.0", required = true }
```

Packages may set `publish = false` to block accidental publishing.

## Package Validation

Validate a package before publishing or using it as a dependency:

```bash
./build/interpreter validate-package packages/examples/hello
./build/interpreter validate-package packages/examples/math
```

Validation checks manifest fields, package identity, reserved namespace rules,
source entrypoints, `package.api.mog`, native ABI compatibility, native export
metadata, and the current native build contract.

Native package builds are V1 CMake-only. Unsupported native build backends are
rejected with a clear validation error.

## Publishing

Publish a source or native package to the configured registry:

```bash
./build/interpreter publish ./packages/acme/util
```

Publish to a specific registry:

```bash
./build/interpreter publish --registry internal ./packages/acme/util
```

Harden publishing with git checks:

```bash
./build/interpreter publish --require-clean-git --tag v1.0.0 ./packages/acme/util
```

Signed publish:

```bash
./build/interpreter publish --signing-key ./keys/release.toml ./packages/acme/util
```

For native packages, publish the current host prebuilt artifact:

```bash
git clone https://github.com/moglang/window.git
cd window
../mog/build/interpreter publish .
```

Publish a prepared prebuilt artifact for another target:

```bash
./build/interpreter publish \
  --target linux-arm64-gnu \
  --native-artifact-dir ./dist/window-linux-arm64 \
  .
```

Publishing is idempotent when an existing `package_id@version` has identical
metadata, dependencies, artifacts, and signatures. Conflicting re-publishes are
rejected.

## Registry Configuration

File registry:

```toml
[registries.default]
index = "./registry"
```

Hosted registry:

```toml
[registries.default]
index = "https://registry.example.com/index.toml"
trusted_keys = ["release-key:BASE64_DER_PUBLIC_KEY"]
```

Login/logout for hosted registries:

```bash
./build/interpreter login default --token "$TOKEN"
./build/interpreter logout default
```

Registry management:

```bash
./build/interpreter registry list
./build/interpreter registry status default
./build/interpreter registry login default --token "$TOKEN"
./build/interpreter registry logout default
```

## Hosted Registry Services

Hosted registries may serve `registry-service.v1` from the registry root:

```toml
schema_version = "registry-service.v1"
artifact_upload_mode = "content-addressed"
index_update_mode = "etag-if-match"
publish_policy = "registry-publish-policy.v1"
```

When present, Mog publishes artifacts to content-addressed
`blobs/sha256/<digest>` paths and updates `index.toml` with ETag guards to
avoid blind overwrites.

If `publish_policy` is present, Mog downloads and enforces
`registry-publish-policy.v1` before upload:

```toml
schema_version = "registry-publish-policy.v1"
require_signed_publish = true
require_clean_git = true
require_tag = true
allowed_namespaces = ["acme", "mog"]
```

If `registry-service.v1` is absent, hosted publishing falls back to the legacy
hosted `index.toml` plus artifact `PUT` workflow.

## Signing and Trust

Registry indexes and artifacts can be signed with Ed25519 registry keys:

```bash
./build/interpreter publish --signing-key ./keys/release.toml ./packages/acme/util
```

Trusted keys can be declared in the project:

```toml
[registries.default]
index = "https://registry.example.com/index.toml"
trusted_keys = ["release-key:BASE64_DER_PUBLIC_KEY"]
```

Hosted registries require trust by default. For explicitly unsigned hosted
registries, use:

```toml
[registries.default]
index = "https://registry.example.com/index.toml"
allow_insecure = true
```

Prefer signed registries for anything beyond local testing.

Bootstrap trust from a hosted registry root:

```bash
./build/interpreter registry trust default --bootstrap
```

This downloads `registry-public-key.v1` and stores the trusted key in the user
registry profile under `~/.config/mog/registries.toml`.

Trust can also be managed explicitly:

```bash
./build/interpreter registry trust default --key release-key:BASE64_DER_PUBLIC_KEY
./build/interpreter registry trust default --key-file ./keys/release-public.toml
./build/interpreter registry trust default --refresh
./build/interpreter registry untrust default --key-id release-key
```

Signed `registry-trust.v1` metadata supports active and revoked registry keys.
Install, audit, and status flows automatically apply trusted registry key
rotation metadata and reject revoked signing keys.

## Project Policy

Projects can enforce package-manager policy in `mog.toml`:

```toml
[policy]
allowed_registries = ["default", "internal"]
allowed_native_namespaces = ["mog", "acme"]
require_locked_in_ci = true
require_signed_artifacts = true
```

Policy behavior:

- `allowed_registries` restricts registry-sourced dependencies
- `allowed_native_namespaces` restricts native packages by namespace
- `require_locked_in_ci` requires `--locked` when `CI` is set
- `require_signed_artifacts` rejects unsigned registry artifacts

Policy is enforced by `mog install` and install-aware `mog run`.

## Audit

Run vulnerability checks against locked registry packages:

```bash
./build/interpreter audit
./build/interpreter audit --offline
```

Registries publish signed `advisories.v1` metadata. Offline audit uses cached
advisory metadata.

## Native Packages

Native packages are first-class package-manager dependencies. They support:

- prebuilt artifacts keyed by target triple
- source-build fallback through the current CMake contract
- `--target`
- `--prefer-prebuilt`
- `--no-native-build`
- `--cmake-toolchain`
- target-specific toolchain config in `[native.toolchains."<target>"]`
- `mog_runtime` compatibility checks
- native ABI validation
- system dependency diagnostics

Example project native toolchain config:

```toml
[native.toolchains."linux-arm64-gnu"]
cmake_toolchain = "./toolchains/linux-arm64.cmake"
generator = "Unix Makefiles"
build_type = "RelWithDebInfo"
configure_args = ["--log-level=NOTICE"]
build_args = ["--verbose"]
env = { "PKG_CONFIG_PATH" = "/opt/sdk/lib/pkgconfig" }
```

For non-host native source builds, Mog looks for toolchains in this order:

1. `--cmake-toolchain <path>`
2. `[native.toolchains."<target>"] cmake_toolchain = "..."`
3. `MOG_CMAKE_TOOLCHAIN_<TARGET>`
4. `.mog/toolchains/<target>.cmake`
5. `toolchains/<target>.cmake`

The official window package is maintained in the standalone [github.com/moglang/window](https://github.com/moglang/window) source repository. The runtime resolves it through an installed, signed registry artifact for ordinary users; Git module dependencies build that repository from source for contributors.

## Tooling Integration

The CLI, runtime, compiler import resolver, and language server share the same
package resolution model. Managed projects resolve through generated install
metadata first, with legacy package-directory scanning retained for tests,
temporary files, and package authoring workflows outside managed installs.

The language server auto-installs dependencies for workspace projects with
`mog.toml` before analysis, then uses the same install metadata as the CLI and
runtime.

## Current Post-V1 Work

The core package manager is V1-complete. Remaining work is follow-on hardening
or ecosystem-scale functionality:

- provenance and transparency records
- organization-wide enterprise trust distribution
- native build backends beyond the current CMake contract
- richer hosted registry service and authentication workflows
- multi-host prebuilt release automation as a registry-level workflow
